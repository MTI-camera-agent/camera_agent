1. 一句话结论

问题 结论
mattpocock/skills 能否直接做「方案迭代 + 团队协作管理」？ 不能单独承担。 它是工程师 ↔ Coding Agent 的可组合技能包（SKILL.md），不是多人文档工作区，也不能替代 Git/Issue/PR。
「分模块出文档 → 主责整合 → 统一实现 → 评估报告」是否合理？ 合理，与 2025–2026 Spec-Driven Development（SDD）方向一致。前提：文档加速对齐 ≠ 弱化 Git；规格与代码都应版本化进仓。
要不要单独工具？ OpenSpec（变更规格）+ Pocock skills（Agent 纪律）+ Git/PR（人协作）；不必上 BMAD 全套。
grill 技能是否采用？ 模块实验默认 grill-with-docs；价值在 grilling 访谈引擎 + domain-modeling 写术语/ADR，不是 1 行 wrapper 本身。
OpenSpec 是否采用？ 是，作为 openspec/changes/ 变更层；与 docs/01 里程碑文档并存。

2. 本地探查：reference/skills

镜像路径：reference/skills。业务仓精选技能已复制到 .cursor/skills/（见 docs/agents/skills.md）。

2.1 机制（读码事实）

grill-me          → 仅 "Run a /grilling session."
grill-with-docs   → "Run a /grilling session, using the /domain-modeling skill."
grilling          → 设计树；frontier 整轮提问；推荐答案；事实 sub-agent 查；
                    shared understanding 确认前不得实现
domain-modeling   → 挑战术语 / 写 CONTEXT.md（纯 glossary）/ 三条件才写 ADR

两者均 disable-model-invocation: true：仅人显式触发。

2.2 适用性评分

维度 grill-me grill-with-docs
模块实验对齐 高 高
沉淀术语/ADR 低 高
多人文档合流 低 中（仍需 SE PR 整合）
替代 Issue/PR 否 否
与 docs/01/p3 中 中–高

结论

  1. 模块实验默认 grill-with-docs。
  2. 纯产品/非代码议题用 grill-me。
  3. 完成评估报告靠 code-review + eval.md，不是 grill。
  4. 文档分流：CONTEXT = 术语；openspec = 行为规格；01 = 里程碑 SoT。

2.3 样例会话 Rubric（待团队实测）

议题示例：「Qwen3.5-9B 统一 Agent vs 外置 DeepSeek」或「Flux-9B 替 Qwen2511 为主示意图栈」。

检查项 通过标准
轮次结构 每轮多问 + 推荐答案
事实 vs 决策 Agent 自查仓内代码/配置
结束门禁 复述 shared understanding；未经确认不改代码
with-docs 产物 CONTEXT 无实现细节；ADR 满足三条件
主责整合 可导出 proposal 要点 → openspec/changes/<id>/

3. 本地探查：reference/openspec

镜像路径：reference/openspec。业务仓已 openspec init（Cursor）；配置见 openspec/config.yaml。

3.1 机制

组件 作用
openspec/specs/<domain>/spec.md 系统当前行为（archive 后累积）
openspec/changes/<name>/ proposal · delta specs · design · tasks
Delta ## ADDED/MODIFIED/REMOVED Requirements + Scenario
/opsx-explore 只思考/读仓；不写代码
/opsx-propose 仅规划；禁止写业务代码
/opsx-apply 按 tasks 实现
/opsx-archive delta 合入 specs；change 移入 archive
Cursor 命令 /opsx-propose 等（见 .cursor/commands/）

3.2 与 Pocock skills 分工

OpenSpec     →  WHAT：变更包、delta、tasks、archive
Pocock grill →  WHY 对齐：访谈、CONTEXT.md、ADR（propose 之前）
Pocock tdd   →  HOW 可靠：apply 阶段红绿重构
Pocock review→  DONE：PR 前 Standards × Spec
Git          →  SoT：规格与代码同仓

3.3 适用性

维度 判定
棕地（已有 docs/01/代码） 强 — 只 spec 即将改的部分
3–5 人并行实验 强 — 每人一个 change folder
替代 Git / 01 否
仪式感 低–中，轻于 BMAD

4. 流程合理性

4.1 应保留

  • 方案文档先行（docs/01、p3_*）。
  • 实验期只产文档，主责统一写生产代码 — 防 AI 加速下的多份实现分叉。
  • 完成评估报告 = SDD 的 verification 环节。

4.2 必须修正

误解 纠正
Git 效率低 → 用文档替代 瓶颈在评审合流；GSD 等反而强调 spec+代码都进 Git
文档放 Notion/飞书即可 Agent/PR 读不到 → 漂移
每人实验顺带 merge 代码 违反 AGENTS.md No version bloat

5. 工具对比（摘要）

工具 类型 CameraAgent
OpenSpec 棕地 delta + change 文件夹 采用（变更规格层）
mattpocock/skills Agent 技能层 精选采用
GitHub Spec Kit 跨 Agent SDD 可选；偏绿场规范化
BMAD 多 Agent 全生命周期 3–5 人过重

6.7 PR / Issue 约定

  • Issue：[openspec:<change-id>] <summary>
  • PR：feat(p3): <summary> (openspec: p3-pr2-coarse-act-cv)
  • PR 体：change 路径、tasks 勾选、eval、pytest 结果（见 模板）
  • Spike：spike/<owner>/<topic>，不 merge

7. 风险

  • 错误规格高速落地 → propose/apply 分离 + SE 批准。
  • OpenSpec 与 01 双写漂移 → archive 时 SE 人工勾选 M 清单。
  • CONTEXT 与 spec 混淆 → CONTEXT 仅术语；行为写 openspec。
  • 多 change 改同一文件 → SE 整合合并或串行 apply。
  • reference 镜像漂移 → 钉 commit（见文首）；定期 git pull in reference/*。
