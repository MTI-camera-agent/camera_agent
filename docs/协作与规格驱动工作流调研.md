## 1. 一句话结论

| 问题 | 结论 |
|------|------|
| [mattpocock/skills](https://github.com/mattpocock/skills) 能否直接做「方案迭代 + 团队协作管理」？ | **不能单独承担。** 它是工程师 ↔ Coding Agent 的**可组合技能包**（`SKILL.md`），不是多人文档工作区，也不能替代 Git/Issue/PR。 |
| 「分模块出文档 → 主责整合 → 统一实现 → 评估报告」是否合理？ | **合理**，与 2025–2026 Spec-Driven Development（SDD）方向一致。前提：**文档加速对齐 ≠ 弱化 Git**；规格与代码都应版本化进仓。 |
| 要不要单独工具？ | **OpenSpec（变更规格）+ Pocock skills（Agent 纪律）+ Git/PR（人协作）**；不必上 BMAD 全套。 |
| grill 技能是否采用？ | **模块实验默认 `grill-with-docs`**；价值在 `grilling` 访谈引擎 + `domain-modeling` 写术语/ADR，不是 1 行 wrapper 本身。 |
| OpenSpec 是否采用？ | **是**，作为 `openspec/changes/` 变更层；与 `docs/01` 里程碑文档并存。 |

## 2. 本地探查：`reference/skills`

镜像路径：[`reference/skills`](../reference/skills)。业务仓精选技能已复制到 [`.cursor/skills/`](../.cursor/skills/)（见 [docs/agents/skills.md](agents/skills.md)）。

### 2.1 机制（读码事实）

```text
grill-me          → 仅 "Run a /grilling session."
grill-with-docs   → "Run a /grilling session, using the /domain-modeling skill."
grilling          → 设计树；frontier 整轮提问；推荐答案；事实 sub-agent 查；
                    shared understanding 确认前不得实现
domain-modeling   → 挑战术语 / 写 CONTEXT.md（纯 glossary）/ 三条件才写 ADR
```

两者均 `disable-model-invocation: true`：**仅人显式触发**。

### 2.2 适用性评分

| 维度 | grill-me | grill-with-docs |
|------|----------|-----------------|
| 模块实验对齐 | 高 | 高 |
| 沉淀术语/ADR | 低 | **高** |
| 多人文档合流 | 低 | 中（仍需 SE PR 整合） |
| 替代 Issue/PR | 否 | 否 |
| 与 `docs/01`/`p3` | 中 | 中–高 |

**结论**

1. 模块实验默认 **`grill-with-docs`**。
2. 纯产品/非代码议题用 **`grill-me`**。
3. 完成评估报告靠 **`code-review` + `eval.md`**，不是 grill。
4. 文档分流：**CONTEXT = 术语；openspec = 行为规格；01 = 里程碑 SoT**。

### 2.3 样例会话 Rubric（待团队实测）

议题示例：「Qwen3.5-9B 统一 Agent vs 外置 DeepSeek」或「Flux-9B 替 Qwen2511 为主示意图栈」。

| 检查项 | 通过标准 |
|--------|----------|
| 轮次结构 | 每轮多问 + 推荐答案 |
| 事实 vs 决策 | Agent 自查仓内代码/配置 |
| 结束门禁 | 复述 shared understanding；**未经确认不改代码** |
| with-docs 产物 | CONTEXT 无实现细节；ADR 满足三条件 |
| 主责整合 | 可导出 proposal 要点 → `openspec/changes/<id>/` |

## 3. 本地探查：`reference/openspec`

镜像路径：[`reference/openspec`](../reference/openspec)。业务仓已 **`openspec init`**（Cursor）；配置见 [`openspec/config.yaml`](../openspec/config.yaml)。

### 3.1 机制

| 组件 | 作用 |
|------|------|
| `openspec/specs/<domain>/spec.md` | 系统**当前行为**（archive 后累积） |
| `openspec/changes/<name>/` | proposal · delta specs · design · tasks |
| Delta | `## ADDED/MODIFIED/REMOVED Requirements` + Scenario |
| `/opsx-explore` | 只思考/读仓；不写代码 |
| `/opsx-propose` | **仅规划**；禁止写业务代码 |
| `/opsx-apply` | 按 tasks 实现 |
| `/opsx-archive` | delta 合入 specs；change 移入 archive |
| Cursor 命令 | `/opsx-propose` 等（见 `.cursor/commands/`） |

### 3.2 与 Pocock skills 分工

```text
OpenSpec     →  WHAT：变更包、delta、tasks、archive
Pocock grill →  WHY 对齐：访谈、CONTEXT.md、ADR（propose 之前）
Pocock tdd   →  HOW 可靠：apply 阶段红绿重构
Pocock review→  DONE：PR 前 Standards × Spec
Git          →  SoT：规格与代码同仓
```

### 3.3 适用性

| 维度 | 判定 |
|------|------|
| 棕地（已有 `docs/01`/代码） | **强** — 只 spec 即将改的部分 |
| 3–5 人并行实验 | **强** — 每人一个 change folder |
| 替代 Git / 01 | **否** |
| 仪式感 | 低–中，轻于 BMAD |

## 4. 流程合理性

### 4.1 应保留

- 方案文档先行（`docs/01`、`p3_*`）。
- **实验期只产文档，主责统一写生产代码** — 防 AI 加速下的多份实现分叉。
- 完成评估报告 = SDD 的 verification 环节。

### 4.2 必须修正

| 误解 | 纠正 |
|------|------|
| Git 效率低 → 用文档替代 | 瓶颈在**评审合流**；GSD 等反而强调 spec+代码都进 Git |
| 文档放 Notion/飞书即可 | Agent/PR 读不到 → **漂移** |
| 每人实验顺带 merge 代码 | 违反 [AGENTS.md](../AGENTS.md) No version bloat |

## 5. 工具对比（摘要）

| 工具 | 类型 | CameraAgent |
|------|------|-------------|
| **OpenSpec** | 棕地 delta + change 文件夹 | **采用（变更规格层）** |
| **mattpocock/skills** | Agent 技能层 | **精选采用** |
| GitHub Spec Kit | 跨 Agent SDD | 可选；偏绿场规范化 |
| BMAD | 多 Agent 全生命周期 | 3–5 人过重 |
| GSD | 执行期上下文隔离 | 借鉴 atomic commit，不必全盘 |
| Git + Issues + PR | 人协作底座 | **必备** |
| Notion/飞书 | 草稿 | 定稿必须进 Git |

## 6. 推荐方案（CameraAgent 3–5 人 · 可实施）

### 6.1 工具栈

| 层 | 选型 |
|----|------|
| 变更规格 | **OpenSpec** — `openspec/changes/<id>/` |
| Agent 纪律 | **Pocock 精选** — `grill-with-docs`、`tdd`、`code-review` |
| 里程碑 | [`docs/01-MVP期-方案设计及计划.md`](01-MVP期-方案设计及计划.md) |
| 术语/ADR | [`CONTEXT.md`](../CONTEXT.md) + [`docs/adr/`](adr/) |
| 代码评审 | Git + PR（[模板](../.github/pull_request_template.md)） |

**文档分流**

```text
CONTEXT.md               → 术语
docs/adr/                → 难逆转决策
openspec/specs/<domain>/ → 可验收行为（SHALL + Scenario）
openspec/changes/<id>/   → 进行中变更包
docs/01 + docs/p3_*      → 里程碑（archive 时 SE 勾选）
```

### 6.2 角色与边界

| 角色 | 代号 | 拥有 | 不做 |
|------|------|------|------|
| 方案与统一实现负责人 | **SE** | Schema/API 锁、change **整合批准**、**唯一 merge 生产代码** | 不独占模型运维 |
| Agent Harness | **Harness** | `workflow/` loop、SkillRegistry、Memory、Wiki | 不改 vLLM 权重 |
| 模型优化 | **Model** | vLLM/ComfyUI、Qwen3.5 统一 Agent、FP8 | 不写 GPU 调度进 agent |
| Skills 实现 | **Skills** | `skills/*.py`、CV/示意图 skill | 不硬编码 provider |
| （可选）Mobile | **Mobile** | `mobile/` Expo overlay | API 契约由 Skills/SE 定 |

**Harness vs Skills**：Harness = 编排注册；Skills = 可替换能力单元。

### 6.3 任务地图（对齐 P3）

| OpenSpec change id | 主责 | 协作 | 优先级 |
|--------------------|------|------|--------|
| `p3-schema-lock` | SE | 全员 | **P0**（并行前必做） |
| `p3-pr1-reference-preview` | Skills | Model, SE | **P0** |
| `p3-pr2-coarse-act-cv` | Skills | Harness, SE, Mobile | **P0** |
| `harness-skill-registry` | Harness | SE | P1 |
| `harness-shooting-act-loop` | Harness | SE, Skills | P1 |
| `model-qwen35-unified-agent` | Model | Harness, SE | P1 |
| `harness-memory-episodic` | Harness | SE | P2 |
| `harness-wiki-reference` | Harness | Skills | P2 |
| `p4-minicpm-fine-act` | Skills | Model, Harness | P3 |

**并行规则**：CV 与 reference preview 可并行 propose，但 **SE 先锁** `schemas/shooting.py` 与 `POST analyze-frame`。

### 6.4 四阶段协作

| 阶段 | 参与者 | 操作 | 产物 | 门禁 |
|------|--------|------|------|------|
| **A. 实验** | 各 lane | `grill-with-docs` + 读 `p3`；可选 `/opsx-explore` | 笔记、CONTEXT 草稿 | 禁止 merge 实现 PR |
| **B. 提案** | 各 lane | `/opsx-propose <change-id>` | proposal, delta specs, design, tasks | propose **禁止写代码** |
| **C. 整合** | **SE** + 全员 | 消冲突；文档 PR review | 批准 change 列表 | **未批准不得 apply** |
| **D. 实现** | SE 指定 implementer | `/opsx-apply` + `tdd` + `pytest` + eval + archive + 代码 PR | 代码+测试+specs 更新 | PR 链 change id |

### 6.5 编制建议

**4 人（推荐）**

| 人 | 角色 | Sprint |
|----|------|--------|
| A | SE | 整合、schema、PR merge、01 勾选 |
| B | Harness | SkillRegistry + shooting act loop |
| C | Model | 服务栈 + Qwen3.5 change |
| D | Skills + Mobile | PR1/PR2 + `mobile/` Phase C |

### 6.6 近 2 周清单

1. **Day 1–2（SE）**：`openspec init` ✅；维护 `openspec/config.yaml`；`CONTEXT.md` + `docs/adr/` ✅
2. **Day 2（SE）**：`/opsx-propose p3-schema-lock` → 评审 → apply
3. **Day 3–5**：并行 propose PR1 / PR2 / harness-skill-registry
4. **Day 6（SE）**：整合 proposal，文档 PR
5. **Week 2**：串行 apply（PR1 测通 → PR2 → registry）；每 change：eval + archive + 更新 `docs/01` §8

### 6.7 PR / Issue 约定

- Issue：`[openspec:<change-id>] <summary>`
- PR：`feat(p3): <summary> (openspec: p3-pr2-coarse-act-cv)`
- PR 体：change 路径、tasks 勾选、eval、`pytest` 结果（见 [模板](../.github/pull_request_template.md)）
- Spike：`spike/<owner>/<topic>`，**不 merge**

## 7. 风险

- **错误规格高速落地** → propose/apply 分离 + SE 批准。
- **OpenSpec 与 01 双写漂移** → archive 时 SE 人工勾选 M 清单。
- **CONTEXT 与 spec 混淆** → CONTEXT 仅术语；行为写 openspec。
- **多 change 改同一文件** → SE 整合合并或串行 apply。
- **reference 镜像漂移** → 钉 commit（见文首）；定期 `git pull` in `reference/*`。
